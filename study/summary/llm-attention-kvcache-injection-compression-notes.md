# 大模型笔记：注意力机制、KV 缓存、提示词注入与上下文压缩

## 笔记概览

这是一份**通用学习笔记**，从底层往上串起四件事，回答一个核心问题——**为什么 AI agent 框架要把"别改前面的对话"当成铁律**：

1. **大模型推理的本质**：猜下一个词的游戏（tokenize → embedding → 逐词预测）。
2. **注意力机制与 QKV 的本质**：Q/K/V 各自是什么、为什么这样设计、因果掩码、多层多头。
3. **KV 缓存**：到底缓存了什么（是 K/V，不是 Q）、为什么要缓存、原理，以及工程上怎么让缓存真的命中。
4. **注入与压缩**：动态内容该注入到哪里才不破坏缓存；以及"上下文压缩"这个**唯一允许破坏缓存**的操作，它的原理和经济账。

笔记会用一个真实的 AI agent 项目（Hermes Agent，Python 实现）的代码作为**举例**，帮助把抽象原理落到工程上。读者**不需要**预先了解这个项目——出现项目代码时，都会先解释它在做什么。文中行号仅供定位，可能随代码演进而变化。

> 适合谁读：理解了"大模型是猜字游戏"、但想搞清楚"缓存到底缓存了什么、为什么改一个字就全废"的学习者。

---

## 一、前置：大模型推理就是"猜下一个词"

文本大模型（基于 Transformer）的推理，本质是一个**猜字游戏**：

```
用户的一大段文字（提示词/任务）进来
  → tokenize（切词）：把字符串切成一个个 token，再查表变成 token id
  → embedding：把每个 token id 查表变成一个高维向量（词向量）
  → 过 Transformer 的几十层，反复计算
  → 预测出"下一个最可能的 token"
  → 把这个新 token 接到末尾，重复上面过程，一个字一个字地生成
```

两个关键认知，后面会反复用到：

- **切词和 embedding 都很便宜**：它们本质是"查表"，几乎不耗算力。
- **真正烧 GPU 的，是"过 Transformer 的几十层、每层做注意力计算"这一步**。这一步在处理"已有的提示词前缀"时，专门有个名字叫 **prefill（预填充）**，是计算大头。

记住这个区分：**省钱省的是 prefill，不是切词/embedding。** 这是很多人对"缓存"的第一个误解。

---

## 二、注意力机制与 QKV 的本质

### 2.1 注意力要解决什么问题

最朴素的想法是"预测下一个词时，前面所有词同等重要"。但这不合理——一句话里，不同的词对当前预测的**重要程度天差地别**。于是引入**注意力机制**：让模型**为每个词动态地决定"该重点看前面哪些词"**。

### 2.2 QKV 各自是什么（本质）

每个词会从自己的表示向量，分别乘上三个**训练学到的权重矩阵** W_Q、W_K、W_V，**同时**生成三个角色向量：

| 角色 | 直觉含义 | 比喻（把词库想成图书馆）|
|---|---|---|
| **Q（Query，查询）** | "我这个词，想查什么？" | 一个读者**这次来想查的问题** |
| **K（Key，索引）** | "我这个词，是关于什么的概括/索引" | 每本书的**概览页/标签**（高度浓缩）|
| **V（Value，内容）** | "我这个词，真正承载的完整信息" | 每本书的**正文内容** |

**它们不在同一个层面上**，理解顺序是：

- **Q 是起点**：处理到当前这个词时，先看它的 Q——它想查什么，这指引了接下来去查谁。
- **K 和 V 是被查询的一套系统**：K 是"概览/索引"，用来快速判断"哪些词和我的查询相关、相关到什么程度"；V 是"正文"，是真正要被取出来融合的信息。

### 2.3 一次注意力的完整流程

```
对当前词 i：
  1. 拿它的 Q_i（我要查什么）
  2. 让 Q_i 和"所有可见词"的 K 逐个算相似度 → 得到一组注意力权重（谁更重要）
  3. 按这组权重，对"所有可见词"的 V 做加权求和 → 提取出信息
  4. 把提取到的信息融合进词 i，得到它的"新表示"
```

> 用比喻说完整：读者 i 带着自己的问题（Q_i）走进图书馆，先扫一遍所有书的概览页（所有 K）判断哪些书相关、排个优先级（注意力权重），再按优先级去读这些书的正文（所有 V），最后把读到的东西综合成自己对这个问题的理解（新表示）。

### 2.4 三个必须补上的精确点（常见误区）

1. **QKV 是同时产生的**：模型不是先有 Q 再生出 K、V。三者由三个权重矩阵**并行**算出。"先 Q 后 KV"只是**理解流程上的角色先后**，不是计算时间上的先后。这三个矩阵怎么把同一个词分化成三种角色——**是训练学出来的**。

2. **因果掩码（causal mask）**：第 i 个词**只能看它自己和它前面**的词（位置 1..i），**看不到后面**的词。这条规则极其重要，因为它意味着：**往后追加新词，不会改变前面已有词的任何表示/K/V**（后面的影响不了前面的）。这是后面"缓存能复用"的根本前提。

3. **多头 + 多层**：上面讲的是"一个注意力头、一层"。真实模型有**几十层**，每层还有**多个注意力头**，每个头各有一套 K/V。所以计算量 = 词数 × 层数 × 头数 × 向量维度——非常庞大。这既是"为什么慢"，也是"为什么缓存很占显存"的原因。

## 三、KV 缓存：缓存什么、为什么、原理

### 3.1 为什么需要缓存

生成是一个字一个字来的。每生成一个新词，注意力都需要用到**前面所有词的 K 和 V**。

- **没有缓存**：每生成一个新词，都要把前面整段重新过一遍所有层、重算所有词的 K/V。前缀有 1 万词，每多说一句就重算 1 万词 × 几十层——巨大浪费。
- **有缓存**：把前缀那些词在**每一层**算好的 K/V **存起来**。生成新词时只算"新增的那几个词"的 K/V，前缀直接复用。

### 3.2 缓存的是 K 和 V，**不是 Q**（关键）

这是最容易搞错的一点，也正是它叫 **KV cache** 而不是 QKV cache 的原因。

判断标准是"**谁会被反复用到**"：

- 生成新词时，是**新词**拿**它自己的 Q**，去查**前面所有词的 K 和 V**。
- 所以前面那些词的 **K、V 会被一批批新词反复用到** → 必须缓存。
- 但前面那些词的 **Q，在它们自己被处理完之后就再也用不到了**。未来的词只用未来自己的 Q → 缓存旧 Q 没有意义，丢弃。

> 图书馆比喻收尾：**K（概览）和 V（正文）是图书馆里的书**，会被一批批新读者反复查阅，所以留在架上（缓存）；**Q 是某个读者这次的查询意图**，他查完就走了，下一个读者用的是自己的查询意图——旧 Q 没有保留价值。

**准确表述**：缓存的 = 前缀里每个词、**在每一层、每个注意力头上的 K 和 V**（不含 Q）。

### 3.3 为什么"改一个字就全废"

你的直觉是对的：**KV 本质是向量，改一个字（哪怕换成同义词）也会让 KV 变，导致重新计算。** 精确机制是：

- 某个词的 K/V，取决于它的表示向量，而表示向量取决于**它和它前面所有词**（因为下层的注意力会融合前面的信息）。
- 所以改了位置 k 的词，会让**位置 k 以及它之后所有位置**的 K/V 全变（因果掩码保证：位置 k 之前的不受影响）。
- 缓存因此从位置 k 起**全部作废**。

这就引出工程上的核心纪律：**前缀必须逐字节稳定，缓存才能命中。**

## 四、工程实现：怎么让缓存真的命中

缓存不是"打个标记"就完事。要真正吃到缓存，工程上要同时守住三层纪律（以 Hermes 这个 agent 项目的对话循环 `agent/conversation_loop.py` 为例）。

### 4.1 第一层：前缀逐字节稳定

- **系统提示（system prompt）一个会话只构建一次，之后每轮逐字节原样复刻**，绝不在对话中途改它（代码注释原文：built ONCE per session, replayed verbatim, so the bytes are byte-stable，约第 793-797 行）。系统提示在最前面，改它会让**整段**缓存作废。
- **新内容只能往列表末尾追加（append-only），不能修改前面已有的消息。**

### 4.2 第二层：把消息字节"洗"成 bit-perfect

即使逻辑内容一样，空白、JSON 字段顺序的细微差异也会让字节不同、缓存不命中。所以发给模型前要**归一化**（约第 843-874 行）：

```python
am["content"] = am["content"].strip()                       # 统一空白
# 工具调用参数：json.dumps(..., separators=(",",":"), sort_keys=True)  # 统一 JSON
```

目的：让每轮前缀**一个字节都不差**。这样不仅云端缓存命中率高，连本地推理服务器（llama.cpp、vLLM、Ollama）的 KV cache 也能复用。

### 4.3 第三层：两种"缓存"要分清

实际系统里常有两层都叫 cache 的东西，别混：

| 名字 | 是什么 | 存在哪 | 人能读吗 |
|---|---|---|---|
| **KV 缓存 / prompt 缓存** | 模型每层的 K/V 注意力向量 | **大模型服务商的 GPU 显存**（应用本机不存）；临时，有 TTL（如 5 分钟/1 小时）| ❌ |
| **应用层对象缓存**（如 Hermes 的 agent 缓存）| 一个活着的会话对象（含已构建好的系统提示等）| 应用进程**内存 RAM** | ❌ |

- **KV 缓存**真正省钱，但它在服务商那边，应用只能通过"发送逐字节一致的前缀 + 缓存标记"去**命中**它，本机不持有任何向量。
- **应用层对象缓存**存在的意义，是**让每轮发出去的文本前缀逐字节一样**，从而让上面那个 KV 缓存命中。Hermes 的 `gateway/run.py`（约第 2610 行）就缓存了每个会话的 agent 对象，注释明确：不缓存的话每条消息都会重建系统提示、破坏前缀缓存、贵约 10 倍。

> 对比另一类东西——**对话历史和长期记忆**：这些是**落盘的、人类可读的文本**（如 Hermes 把历史存进 SQLite `state.db` 的 `messages` 表、把记忆存进 `MEMORY.md`）。它们**不是**向量、**不是** KV 缓存，每轮被当作**文本**拼进提示词发给模型。**永久文本（历史/记忆）和临时向量（KV 缓存）是两回事，别混。**

## 五、注入：动态内容该放在哪里

Agent 每轮往往要给模型补一些**动态内容**：相关的长期记忆、检索到的资料、插件提供的上下文、用户中途插入的引导等。**放在哪里注入，直接决定缓存还命不命中。** 三条规则（以 Hermes 为例）：

1. **稳定内容（系统提示）钉死不动**——它是缓存前缀的最前面，绝不中途改。

2. **每轮的动态内容，拼到"当前这条用户消息的末尾"，而不是系统提示**（约第 742-758 行）。因为：
   - 注入系统提示 = 改最前面 = 整段缓存作废；
   - 拼到最新用户消息末尾 = 只影响**结尾**那段（本来就没缓存的部分），前面的缓存全保住。
   - 而且注入是**"发送时拼在副本上"**：原始消息列表不被改，所以注入的内容**不会漏进持久化的历史**（临时给模型看，不污染存档）。

3. **对话中途的临时引导，搭车在已有的"工具结果消息"上，不新建用户消息**（约第 650-699 行）。因为大多数对话 API 要求**消息角色严格交替**（不能连续两条同角色），循环中途硬插一条用户消息会破坏交替；搭车在已有消息上则不会。

> 一句话心智模型：把对话想成一摞卡片。最底下的"设定卡"（系统提示）贴死不动；每轮临时给模型看的便签夹在**最新那张卡的复印件**里、原件不动；中途的临时指令写在**最近一张工具结果卡的背面**，绝不硬塞一张新卡打乱顺序。**全部都是为了护住前缀缓存 + 不破坏角色交替。**

## 六、压缩：唯一允许"破坏缓存"的交易

### 6.1 它不是魔法，是主动做的交易

对话会越来越长。但前面所有纪律都在说"别改前缀"。那对话长到装不下时怎么办？答案是**上下文压缩**——而它**恰恰要改最前面的旧消息**，所以会把缓存**几乎全炸掉**。

**压缩没有绕过缓存失效。** 它是用"**一次缓存损失**"，换"**两样更重要的东西**"的交易。这就是为什么它常被称为"唯一允许改动上下文的例外"。

### 6.2 压缩在做什么（机制）

以 Hermes 的 `agent/conversation_compression.py` 为例：

```
对话太长 [系统, 旧1, 旧2, ..., 旧40, 近41, ..., 近50]
        ↓ 超过 token 阈值，触发压缩
用一个便宜的"辅助模型"把较早的 [旧1..旧40] 读一遍，总结成一段简短摘要
        ↓ 重建列表
新列表 [系统, 摘要(旧1..旧40), 近41, ..., 近50]
```

- 较早的一大坨旧消息 → 被**一段简短摘要**取代（如 80k token 压成 5k token）。
- 最近的若干轮 → **原样保留**（近期细节对当前任务最重要）。
- 用**辅助模型**单独总结，不占主对话。
- 兜底：辅助模型若连这段都装不下，就**直接丢中间几轮、不做摘要**（降级）。

### 6.3 为什么这笔交易划算——两个理由

1. **首要：不压缩，对话会物理上装不下。** 模型有**硬性上下文窗口上限**（如 20 万 token），长对话迟早超过它，模型**根本无法接收**，对话直接死。压缩首先是为了**让对话活过上限**，缓存失效是"为活命"付的代价。

2. **其次：一次性成本，换之后每轮都便宜（摊销）。**

   ```
   不压缩：涨到 100k，之后每轮都扛 100k 前缀；缓存一过期就重 prefill 100k，且越来越逼近上限
   压缩：  一次性付 = 总结一次 + 新前缀(25k)重 prefill 一次（缓存 miss）
           之后每轮 = 只扛 25k → 每轮便宜约 4 倍，还买回约 175k 余量
   ```

   付**一次**缓存 miss + **一次**总结调用，换"对话能继续活 + 之后每轮 4 倍便宜"。轮数越多，一次性成本摊得越薄。

### 6.4 一个精妙点：缓存被"重置"到更小的新基线

压缩把旧前缀炸了，但**新前缀（系统 + 摘要）压缩完就固定下来**，成为新的稳定前缀。之后追加的新消息又能在**这个更小的新前缀**上重新命中缓存。

> 所以不是"压缩 = 从此没缓存"，而是"**缓存被重置到一个更小的新基线上，然后重新积累**"。付一次重置的钱，换一个更小、更省的新起点。压缩因此是一个**显式的、刻意选择的缓存断点**——只在这个最值得破缓存的时刻才破。

## 七、把整条线串起来

1. **底层**：模型是猜字游戏；真正烧算力的是 prefill（过几十层算注意力），不是切词/embedding。
2. **注意力**：每个词生成 Q/K/V；用自己的 Q 查所有词的 K 得权重，再按权重取所有词的 V 融合成新表示。**因果掩码**保证"往后追加不扰动前缀"。
3. **缓存**：缓存的是前缀每个词、每层、每头的 **K/V（不含 Q）**；改一个字节，从该位置起缓存全废。
4. **工程命中缓存**：① 系统提示逐字节复刻、append-only；② 消息字节归一化成 bit-perfect；③ 分清"服务端 KV 缓存"和"应用层对象缓存"。
5. **注入**：动态内容拼最新用户消息末尾（且在副本上）、中途引导搭车工具消息——都为护前缀缓存 + 不破角色交替。
6. **压缩**：唯一允许破前缀的时刻——不破就撞上限/无限变贵；破一次换"能活 + 之后更便宜 + 更小的新缓存基线"。

**一句话总纲**：前面所有"别动前缀"的纪律，都是为了尽量**晚、少**地走到压缩这一步；一旦非走不可，压缩就是那笔"破一次缓存、买回生存和长期便宜"的划算交易。

## 附：关键术语表

| 术语 | 一句话解释 |
|---|---|
| **token** | 文本被切成的最小单位；先变成 id，再查表变成词向量 |
| **embedding** | token id → 高维向量的查表过程；很便宜 |
| **prefill** | 把已有提示词前缀过一遍所有层、算出 K/V 的阶段；计算大头 |
| **Q / K / V** | 查询 / 索引 / 内容；每个词由三个训练好的矩阵同时生成 |
| **因果掩码** | 每个词只能看自己和前面的词；保证追加不扰动前缀 |
| **KV 缓存** | 缓存前缀每词每层每头的 K/V（不含 Q）；省 prefill |
| **prompt 缓存** | 服务商侧对相同前缀复用 KV 缓存的能力；有 TTL |
| **bit-perfect 前缀** | 逐字节完全一致的前缀；缓存命中的前提 |
| **append-only** | 只往消息列表末尾加、不改前面；保护缓存 |
| **角色交替** | 消息 user/assistant/tool 不能连续两条同角色；多数 API 的硬要求 |
| **上下文压缩** | 把较早历史总结成摘要、重建更短列表；唯一允许破前缀缓存的操作 |
